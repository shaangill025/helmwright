# Owner decisions

Decisions the owner made for helmwright, with the options that were rejected. Design references
(`03§`, `06§`, …) point to the Meta-Harness Design v2 sections; "Sept" is the September 2026
requirements document. This log is a stopgap until the decision ledger (Slice A) exists.
`docs/design-trace.md` maps each design requirement to its status.

The log has two parts:

- **Harness decisions** say what helmwright does. They implement, or deviate from, the design.
- **Development process decisions** say how this repository is built. They bind the development
  agent and the owner, not the harness. Rules inside the harness about who may change what (Ring 0,
  always-ask, permission tiers) are harness decisions.

## Deviations from the design

Only the items in this table deviate from Design v2. Every other harness decision implements the
design default or makes a choice that the design leaves open. The dogfood targets row replaces a
second target named in 08 that has nothing to do with this project; the owner decided that this is
not a deviation.

| Decision             | Design says                                                                | helmwright does                                                                                                                                                                  | Review point                                                                                                                                                                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native engine models | 10§Roles and 06§Hands: two-tier model routing per role                     | `claude-opus-5-5` for every role, effort set per role                                                                                                                            | M1 "what can we stop doing" review, with measured cost per completed task                                                                                                                                                                                                                                              |
| X2 API transport     | 06§Ring 0 contents: one authenticated state/action API under every surface | In-process typed dispatcher without authentication until B13 (M1); owner-only writes rest on presence-signed owner events (Owner answer signatures) plus the Q46 import boundary | B13 (M1): the hosted engine's MCP bridge is the first second-process surface, so the 0600 socket with a peer-UID check arrives with it (X2 rule) and, together with the presence-signed owner events that start in M1 (Owner answer signatures), closes this deviation; peer-UID alone does not authenticate the owner |

Known conflict, not yet a deviation: the devil's advocate (04§Loop 2) needs a second model family,
and 10's M2 Reviewer wants a model family different from the worker's where possible, but the
native engine uses one model. The owner decides at the M2 scope review.

### Packaging and agent plugins (2026-10-06)

Design v2 does not cover distribution or agent plugins. These decisions extend the design in an area
it leaves open, so they are not deviations. Two terms: in **engine mode** helmwright drives a native
or hosted engine as a hand behind `execute` (the Hosted engine row: built-in tools disabled); in **plugin mode** the
developer works in the agent with its own tools, and helmwright is reached through an agent plugin.
Agent plugins are not 10's "Capability plugins" or 05's Ring 2 plugin kinds. Third-party facts below
are from vendor documentation read on 2026-10-06 (Claude Code checked directly; Codex and Pi from
research only); each agent's conformance test confirms them before release.

Each plugin passes a conformance test for its agent before release, in the same way as engine admission (Q1 capability matrix, Q22 attestation)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | surface only (no guard hooks); no plugins; Claude Code first and the others in M3; all in M3                                                                                                                                                                                                                                               |
| Owner answer signatures | From M1, every owner event (`decision.owner.*`) carries a presence signature. On macOS a small Swift helper in the repo (built locally with the Xcode Command Line Tools) signs with a Secure Enclave P-256 key whose access control needs Touch ID or the owner's password for each use; the private key never leaves the chip. The helper's prompt shows the exact answer that it signs (for example "Approve option B on card #12"). The signed payload binds the card ID, the action, a hash of the chosen option and any owner text, the run ID and a single-use nonce, so a signature cannot move to another card or answer. The kernel rejects an owner event without a valid signature. Linux owners (from M2) use a FIDO2 security key for presence. Reason: an agent with a host shell runs as the owner's OS user (in M1 the Q57 baseline arm and any agent that works on the repository; from M2 also plugin mode), so peer-UID checks, terminal confirmations (an agent can open a pseudo-terminal) and import boundaries cannot tell the agent from the owner; only user presence can, while helmwright's own code, pinned key and helper are intact. The TUI and the CLI answer handler (Q46) both obtain the signature; the TUI is the primary surface, and the MCP server has no answer tool. SIG requirements: the owner public key is pinned at setup, and rotating it needs a signature from the current key; software keys are refused outside test builds; the helper's binary digest is pinned and checked before each use; signatures are verified on every write, every projection rebuild and every replay, so an event inserted directly into the database is rejected. Residual risk: a same-user process that can change helmwright's own code, the pinned key or the helper can defeat in-process checks; the signatures make such a change detectable, not impossible. Running the kernel as a separate OS user would close this; the owner decides that at the start of SIG. CI tests the helper on a macOS runner with a software test key; real Touch ID is tested locally only | TUI terminal confirmation only (a speed bump, not a guarantee); refuse owner answers while a plugin session is connected; answers also in the agent chat; unsigned owner events in M1 with a documented risk; isolating only the baseline arm; an npm native-addon signer; a Keychain secret behind a password dialog; macOS only until M5 |
